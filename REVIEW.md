# Review

## What matters
- Skillabel is run on skills written by strangers. Every file under a scanned folder is hostile input: its name, its text, its size, and whether it is a link.
- It never runs a skill and starts no other program. There is no `subprocess`, `os.system`, `eval` or `exec` in the package. The one outside effect is `webbrowser.open` on the report `auto` just wrote (`cli.auto`).
- It never follows a link or junction inside a folder it scans, to read or to write (`safeio.is_link`, `safeio.walk_files`, `safeio.read_capped`). A linked file becomes a `linked-file` finding. A linked `SKILL.md` or a linked skill folder becomes a label that says "not checked" and makes no risk claim (`deterministic.failed_label`, `deterministic.linked_folder_label`). The one exception: `auto` follows a link that sits directly inside `~/.claude/skills`, `~/.agents/skills` or `~/.codex/skills` and points to a folder with a `SKILL.md`, and nothing below it. Every link it does not follow is named and counted, and `lint` lists it as a warning, so `--strict` fails on it.
- Every write goes through `safeio.safe_write_text` or `safeio.safe_mkdir`, which refuse a target that passes through a link inside the scanned folder, in any letter case or Windows spelling of that folder (`safeio.check_write_target`). `tests/test_hostile.py` and `tests/test_hostile_recheck.py` are the proof on Windows and Linux.
- Every read is capped (`parse.MAX_*`): 1 MiB per file, 8 MiB and 2000 files per skill, 12 folders deep. A file that is skipped is named on the label with the reason. Nothing is dropped without a line saying so.
- Frontmatter is parsed with a safe YAML loader that refuses aliases (`parse._NoAliasLoader`).
- The tool reports surface area with evidence, never a verdict. No field, badge or sentence says "safe" or "unsafe". "No pattern matched" means only that, and the README says what was not read.
- A risk flag from the text patterns (`riskscan.regex_risk`) is never removed or weakened by the AI layer (`ai._merge_risk`). An AI fact that cites a line that does not exist is dropped. What the AI wrote is marked as an AI summary wherever it is shown.
- Nothing leaves the machine without `--ai`. With it, skill text goes only to the provider that `providers.py` resolves, and one line names the provider and where its key came from (`cli._say_provider`).
- The provider and key come only from the process environment. Skillabel never opens, stats or reads a `.env` file, anywhere: a file or folder named `.env` or `.env.*` is passed over by its name alone (`safeio.is_env_file`), and a skill folder with such a name gets a "not checked" label (`deterministic.env_named_folder_label`). `tests/test_dotenv.py`, `tests/test_hostile_dotenv.py` and `tests/test_e1_env_folders.py` are the proof.
- Text from a skill never reaches the terminal, the HTML report or the PR comment raw. The terminal goes through `terminal.safe`, the report through Jinja autoescape (`report.py`), the comment through `comment.text` and `comment.code`, and a word that could mention a person or link an issue is shown as code. `tests/test_hostile_terminal.py`, `tests/test_hostile_label.py` and `tests/test_comment.py` are the proof.
- The Action writes nothing into the checked-out pull request. Its output goes under `$RUNNER_TEMP/skillabel`. No `${{ }}` value is expanded inside a `run:` block. Actions are pinned to full commit IDs, and dependencies install from hashed, wheel-only requirement files. While it prints skill text, GitHub's workflow commands are stopped with a random token (`action.yml`, `tests/test_action.py`).
- A skill touched by a pull request is always in the comment: any changed file under its folder counts (`comment.changed_holders`), so does a changed file outside it that its text points to (`comment.points_to_a_change`, worked out from the path alone, never opened), and a skill that could not be checked is shown as not checked, never left out.
- Usage counts read only skill names and dates from the session logs (`usage.py`). No prompt or message text is parsed, kept or shown.
- Error messages are for the person at the terminal: what went wrong and the next command to run.

## Known noise
- The text patterns can be dodged by a skill that splits or encodes a command. That is stated in the README under "What 'checked' covers". A finding that says so needs a new pattern with a test, not a claim that the scan is broken.
- The fixtures under `tests/fixtures/` and the folders the hostile tests build are hostile on purpose: `wolf` and `scary` run shell and reach the network in their text. They are data, never run.
- The Action's steps are tested by running their scripts locally (`tests/test_action.py`), and it was run on GitHub's own runner in a private test repo (2026-11-23): install, comment, report upload, the lint gate and the stopped workflow commands all held. A finding about runner behaviour needs evidence from a real run.
- The session log formats in `usage.py` mirror what Claude Code and Codex write today. We do not control them.
